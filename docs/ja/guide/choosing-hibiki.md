# Hibikiを選ぶ条件

複数のWebhookプロバイダーを共通の型付きAPIで扱いたい場合や、Core・プロバイダーの実行時依存を増やさず、Web標準のRequest/Responseで処理したい場合にHibikiが向いています。HonoとHibikiは併用できます。

| 選択肢 | 向いている用途 | アプリ側で扱う責任 |
| --- | --- | --- |
| 公式SDK | 単一プロバイダー。APIクライアントをすでに使っている場合 | フレームワークとの接続、イベント振り分け、テスト |
| Hibiki | 複数プロバイダー、共通の処理モデル、依存を抑えたい環境 | 業務データの検証、保存、重複排除、キュー、再試行 |
| 直接実装 | 範囲が狭く、固有の要件がある処理 | 署名方式の正しさ、仕様更新、振り分け、型、テスト |
| Webhook基盤サービス | 永続的な配信管理、監視、再実行が主な要件 | 業務処理と基盤への接続 |

これは選定条件の整理です。実装量や性能の優位性を測定した結果ではありません。エージェントの成功率と作業コストは、リポジトリの`evals/`で別途測定します。

## 導入前に対応範囲を確認する

- Stripeは、`type`と`data.object`を持つsnapshotイベントの一部に対応しています。thinイベントには対応していません。
- GitHubは、JSON形式のイベントとactionの組み合わせの一部に対応しています。フォーム形式は対象外です。
- Discordは、署名付きInteractionsを受け取ります。`createDiscordWebhook`によるincoming webhookへのメッセージ送信は別のAPIです。

[対応範囲のJSON](/providers.json)にパッケージバージョンとイベント名を載せています。導入するバージョンと照合してください。

payloadの型は構造の一部を定義したものです。決済状態・金額やIssue・Pull Requestの主要フィールドに型があり、その他は`unknown`です。追加フィールドは古いpayloadや小さなテストデータも扱えるよう、省略可能にしています。実行時の検証機能ではありません。HibikiがStripeのAPIバージョンを指定することもありません。バージョン固有のデータが必要な処理では`event.api_version`を確認し、業務に必要な値を検証してください。

## 実際のルートと副作用をテストする

[testing](/ja/reference/testing)で署名付きのリクエストを作り、実際のルートと副作用を確認できます。プロバイダーのアカウント、トンネル、開発サーバーは不要です。実サービスの設定や、デプロイ先の互換性は別途確認します。

[Honoの統合例](https://github.com/hibiki-js/hibiki/tree/main/examples/hono-webhooks)では、秘密鍵と業務処理を注入し、外部通信なしで両プロバイダーを検査しています。リポジトリでは`pnpm check:examples`、または`pnpm exec vitest run examples/hono-webhooks`で実行できます。
